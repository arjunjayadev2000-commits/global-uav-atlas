# Building the Power BI file

The submission asks for a `.pbix`. A `.pbix` is a binary artefact that only Power
BI Desktop can author, so this repository produces **what a `.pbix` is built
from**: a clean star schema, the DAX for every measure, the relationship list,
and this guide. Expect about 15 minutes end to end.

Everything referenced here is in `outputs/powerbi/`, generated by
`python run.py --all` (or `python run.py --stage powerbi`).

---

## 1. Load

**Get Data → Text/CSV → Folder**, point at `outputs/powerbi/`, load these 15
tables:

| Kind | Tables |
|---|---|
| Dimensions | `dim_date`, `dim_corridor`, `dim_admin_unit`, `dim_vessel_class`, `dim_event_type` |
| Bridge | `bridge_admin_corridor` |
| Facts | `fact_conflict_weekly`, `fact_detections`, `fact_cells`, `fact_corridor_pressure`, `fact_msri`, `fact_dark_clusters`, `fact_traffic_deficit`, `fact_forecast`, `fact_forecast_scores` |

In Power Query, set `date`, `week_ending`, `week`, `detection_date` and
`timestamp` to **Date** or **Date/Time**, and `is_dark`, `is_solas`,
`is_dark_spot`, `critical`, `likely_fishing` to **True/False**. Nothing else
needs transforming — the export is already tidy.

Mark `dim_date` as the date table (**Table tools → Mark as date table**, column
`date`).

## 2. Model

Create the relationships in `relationships.csv`. The two that matter:

* **One date dimension drives everything.** `dim_date[date] → fact_detections[detection_date]`
  (daily) and `dim_date[week_ending] → fact_corridor_pressure[week]` (weekly), so
  a single slicer moves the whole report. For `fact_conflict_weekly[week]`, join
  on `dim_date[week_ending]`.
* **Admin units to corridors is many-to-many, and must stay that way.** One
  admin unit can threaten several corridors (Yemen's Al Hudaydah sits on both
  Bab-el-Mandeb and the Southern Red Sea). The relationship therefore runs
  through `bridge_admin_corridor`, which carries `distance_km` and
  `decay_weight`. Flattening it onto the fact table would double-count events —
  this is the single easiest way to get a wrong number out of this model.

Set every dimension→fact relationship to single-direction (1:*), except
`bridge_admin_corridor`, which needs bidirectional filtering or the
`CROSSFILTER` in the measure provided.

## 3. Measures

Open `measures.dax` and paste each block in as a new measure. They are grouped:

* **Conflict** — `Events`, `Fatalities`, `Lethality`, `Events 4W`, `Events YoY %`, `Escalation Flag`
* **Maritime** — `Detections`, `SOLAS Detections`, `Dark Detections`, `Dark Rate`,
  **`SOLAS Dark Rate`** (the headline), `SOLAS Dark Rate vs Baseline`, `Detections Per Scene`
* **Dark spots** — `Dark Spot Cells`, `Mean SDR`, `Behavioural Dark Spots`
* **Risk** — `MSRI`, `India Exposure`, `Red Tier Corridors`, `Risk Tier Colour`
* **Bridge-aware** — `Corridor Events`, `Corridor Events Weighted`

`SOLAS Dark Rate` is the measure to put on the front page. `Dark Rate` without
the size filter will mislead anyone reading it, for the reason set out in
`docs/METHODOLOGY.md` §3.

## 4. Suggested four pages

**Page 1 — Command picture.**
Cards: `SOLAS Dark Rate`, `Red Tier Corridors`, `Behavioural Dark Spots`,
`Detections`. Map (`fact_cells`, bubble at `cell_lat`/`cell_lon`, size
`detections`, colour `sdr`). Bar of `MSRI` by `dim_corridor[chokepoint]` using
`Risk Tier Colour` for conditional formatting. Date slicer from `dim_date`.

**Page 2 — Identification picture.**
Bar of `SOLAS Dark Rate` by corridor with a reference line at the open-ocean
baseline. `fact_cells` table filtered to `area_type`, so a reader can flip
between dead zones and behavioural dark spots. Scatter of `sdr` against
`detections`, `area_type` on colour.

**Page 3 — Traffic and displacement.**
`fact_traffic_deficit`: `deficit_pct` by corridor as a diverging bar. Detections
per scene by corridor. A `fact_detections` map filtered to `is_solas` with a
`chokepoint` slicer for the Red Sea corridors.

**Page 4 — Conflict and outlook.**
`Events` by week (line) with `dim_event_type` as a legend. `Corridor Events` by
corridor using the bridge. `fact_forecast` as a line with `lower`/`upper` as a
shaded band, and `fact_forecast_scores` beside it as a small table so the reader
can see which model won and by how much.

## 5. Colour, so the report reads as one system

The figures use a validated palette; matching it keeps the Power BI file and the
PDF visually consistent.

| Role | Hex |
|---|---|
| Series 1 / sequential dark end | `#2a78d6` |
| Series 2 | `#eb6834` |
| Series 3 | `#1baf7a` |
| Sequential light end | `#cde2fb` |
| RED tier | `#d03b3b` |
| AMBER tier | `#fab219` |
| GREEN tier | `#0ca30c` |
| Page background | `#fcfcfb` |
| Primary text | `#0b0b0b` |
| Gridlines | `#e1e0d9` |

Two rules worth keeping: never put two different measures on twin y-axes, and
always pair a tier colour with its text label — the tier colours are reserved for
status and should never be reused for a data series.

## 6. Refreshing

Re-run `python run.py --all` and hit **Refresh** in Power BI Desktop. Table names
and column names are stable across runs by design, so a refresh never breaks the
model.
